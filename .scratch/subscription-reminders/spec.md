# Сервис напоминаний о подписках

## Problem Statement

Нужно получить простой C# сервис по согласованным требованиям и затем показать, насколько полученный код этим требованиям соответствует. Без точного API и проверяемых правил сравнение результата генерации с ТЗ будет субъективным.

## Solution

Сервис хранит ближайший платёж каждой подписки и по заданной дате возвращает платежи, которые наступят в ближайшие три календарных дня. Пользователь управляет подписками через JSON API. Сопоставление с ТЗ проводится через HTTP-проверки, модульные тесты бизнес-логики, проверку схемы БД и ревью архитектуры. Реализация и проверки выполняются только по следующей команде пользователя.

## User Stories

1. Как клиент API, я хочу видеть три доступных сервиса, чтобы выбрать вид подписки.
2. Как клиент API, я хочу создать подписку для одного из сервисов, чтобы сохранить ближайший платёж.
3. Как клиент API, я хочу хранить сумму в целых копейках, чтобы не получать ошибки округления.
4. Как клиент API, я хочу задавать дату в привычном формате YYYY-MM-DD, чтобы не кодировать её числом вручную.
5. Как клиент API, я хочу видеть все подписки в стабильном порядке, чтобы сверять сохранённые данные.
6. Как клиент API, я хочу изменить сервис, сумму или дату подписки, чтобы поддерживать данные актуальными.
7. Как клиент API, я хочу удалить подписку, чтобы она больше не попадала в напоминания.
8. Как клиент API, я хочу получить напоминания для явно указанной даты, чтобы проверить ближайшие платежи.
9. Как клиент API, я хочу видеть платежи с сегодняшнего дня по третий день включительно, чтобы не пропустить срок оплаты.
10. Как клиент API, я хочу получать пустой список, если подходящих платежей нет, чтобы отличать его от ошибки.
11. Как клиент API, я хочу получать ошибку для неизвестного сервиса, неположительной суммы и неверной даты, чтобы исправить запрос.
12. Как клиент API, я хочу получать 404 для отсутствующей подписки, чтобы не считать изменение или удаление успешным.
13. Как клиент API, я хочу сохранять подписки после перезапуска сервиса, чтобы не вводить их снова.
14. Как проверяющий, я хочу видеть соответствие HTTP-ответов конкретным правилам ТЗ, чтобы оценить результат генерации.
15. Как проверяющий, я хочу проверить типы столбцов и связи БД, чтобы подтвердить отсутствие строковых полей.
16. Как проверяющий, я хочу проверить границы трёхслойной архитектуры и интерфейс репозитория, чтобы оценить реализацию отдельно от поведения.
17. Как проверяющий, я хочу сохранить результаты проверок и ревью в отчёте, чтобы объяснить, как получен вывод о соответствии.

## Implementation Decisions

- Реализация планируется на ASP.NET Core с тремя слоями: API, бизнес-логика и доступ к данным.
- Слой бизнес-логики обращается к хранилищу только через `ISubscriptionRepository`; реализация интерфейса работает с PostgreSQL. Зависимости регистрируются при запуске.
- БД содержит ровно две таблицы: `Services` с целочисленным ключом и `Subscriptions` с целочисленными `Id`, `ServiceId`, `AmountCents` и столбцом `NextPaymentDate DATE`. `ServiceId` — внешний ключ; сумма положительна. Строковых столбцов нет.
- Доступны три сервиса: 1 — музыка, 2 — видео, 3 — облако. Названия определены в коде; несколько подписок могут относиться к одному сервису.
- В C# дата представлена `DateOnly`, в JSON — строкой YYYY-MM-DD. После оплаты клиент сам обновляет дату следующего платежа.
- Контракт API: `GET /services`, `GET /subscriptions`, `POST /subscriptions`, `PUT /subscriptions/{id}`, `DELETE /subscriptions/{id}`, `GET /reminders?date=YYYY-MM-DD`. Полные тела запросов и ответов задаёт согласованное ТЗ.
- Напоминания включают даты от `date` до `date + 3` календарных дня включительно. Список подписок упорядочен по `Id`, напоминания — по дате, затем по `Id`.
- Успешное создание возвращает 201, изменение и чтение — 200, удаление — 204. Неверный ввод возвращает 400, отсутствующий `id` — 404. Для `PUT` тело проверяется до поиска `id`. Ошибки имеют JSON-поле `error`; пустой список — `[]`.

## Testing Decisions

- Основная граница проверки поведения — HTTP API. Проверки сравнивают наблюдаемые ответы и состояние после запросов, без привязки к внутренним методам.
- На HTTP-границе проверяются полный каталог сервисов, создание, чтение, изменение, удаление, ошибки, сортировка, формат дат и пустые ответы.
- Для напоминаний проверяются четыре даты вокруг границ интервала, а также переход месяца и года.
- Отдельный модульный тест бизнес-логики подменяет `ISubscriptionRepository` и проверяет правила выбора напоминаний и валидации. Это вторая граница, необходимая для предусмотренных заданием показателей покрытия.
- Интеграционная проверка перезапуска подтверждает сохранение данных в PostgreSQL; запрос схемы подтверждает тип `DATE`, целочисленные столбцы и внешний ключ.
- Архитектура проверяется по зависимостям слоёв и возможности подменить репозиторий. Такой вывод дополняет поведенческие тесты.
- Целевые показатели следующего этапа: не менее 80% ветвей и 90% операторов бизнес-логики. Тесты должны подтверждать правила, а не повторять код реализации.
- В первой части проекта есть примеры модульных тестов C# с подменой зависимостей; их стиль можно использовать как ориентир, не перенося предметную область заказа в подписки.
- Для каждого требования в отчёте фиксируются проверка, фактический результат и вывод о соответствии.

## Out of Scope

- Пользовательский интерфейс, отправка сообщений, автоматическое списание и автоматический пересчёт следующей даты.
- Генерация OpenAPI.
- Реализация сервиса, запуск тестов и написание отчёта в рамках текущего вызова `to-spec`.

## Further Notes

Согласованное ТЗ является источником точного API-контракта. Промпт для генерации пользователь удалил из ТЗ; этот документ его не восстанавливает. Перед фактической генерацией кодового решения промпт и результаты работы потребуется отдельно зафиксировать в отчёте.
