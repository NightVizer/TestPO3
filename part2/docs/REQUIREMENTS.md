# ТЗ: сервис напоминаний о подписках

## Назначение

Сервис хранит ближайший платёж по подписке и по запросу выдаёт список платежей, которые наступят в течение трёх дней. Напоминание — запись в ответе API; отправка сообщений и интерфейс пользователя не требуются.

## Данные

Реляционная БД PostgreSQL, две таблицы, связь один ко многим:

| Таблица | Поля | Ограничения |
|---|---|---|
| `Services` | `Id` — целое число | Первичный ключ. При запуске доступны записи `1` (музыка), `2` (видео), `3` (облако). |
| `Subscriptions` | `Id`, `ServiceId`, `AmountCents` — целые числа; `NextPaymentDate` — `DATE` | `Id` — первичный ключ; `ServiceId` — внешний ключ на `Services.Id`; `AmountCents > 0`. |

В C# дата имеет тип `DateOnly`, в БД — `DATE`, в API — строка формата `YYYY-MM-DD` (например, `2026-11-14`). В таблицах нет строковых столбцов; названия трёх сервисов задаются в коде и в БД не хранятся. Несколько подписок могут относиться к одному сервису. Периодическое списание автоматически не рассчитывается: после оплаты клиент обновляет дату следующего платежа.

## Правила

1. Подписку можно создать, получить в списке, изменить и удалить.
2. При создании и изменении `ServiceId` должен существовать в `Services`, сумма должна быть положительной, дата — допустимой.
3. Для заданной даты `date` напоминания включают подписки с `NextPaymentDate` от `date` до `date + 3 календарных дня` включительно. Просроченные платежи не включаются.
4. Списки подписок сортируются по `Id`; напоминания — по `NextPaymentDate`, затем по `Id`. Данные сохраняются между перезапусками сервиса.

## API

Все запросы и ответы с телом используют JSON. Числа передаются числами, дата — строкой строго в формате `YYYY-MM-DD`.

| Метод и путь | Вход | Успех | Ошибка |
|---|---|---|---|
| `GET /services` | — | `200`: `[{"id":1,"name":"музыка"},{"id":2,"name":"видео"},{"id":3,"name":"облако"}]` | — |
| `GET /subscriptions` | — | `200`: массив подписок | — |
| `POST /subscriptions` | `{"serviceId":1,"amountCents":29900,"nextPaymentDate":"2026-11-14"}` | `201`: созданная подписка с `id` | `400`: неверные данные |
| `PUT /subscriptions/{id}` | Те же три поля, что при создании | `200`: обновлённая подписка | `400`: неверные данные; `404`: нет `id` |
| `DELETE /subscriptions/{id}` | — | `204` | `404`: нет `id` |
| `GET /reminders?date=2026-11-10` | Обязательный параметр `date` | `200`: массив объектов `{"subscriptionId":1,"serviceId":1,"amountCents":29900,"nextPaymentDate":"2026-11-12"}` | `400`: дата отсутствует или неверна |

Подписка в ответе: `{"id":1,"serviceId":1,"amountCents":29900,"nextPaymentDate":"2026-11-14"}`. Пустой список возвращается как `[]`. Ошибки имеют тело `{"error":"краткое описание"}`. `id` в пути — положительное целое число; иначе `400`. Для `PUT` сначала проверяется тело запроса, затем наличие `id`.

## Архитектура

ASP.NET Core, три слоя: **API** принимает HTTP и формирует ответы; **бизнес-логика** проверяет данные и выбирает напоминания; **доступ к данным** работает с PostgreSQL. Бизнес-логика обращается к БД только через интерфейс репозитория `ISubscriptionRepository`; реализация интерфейса находится в слое доступа к данным. Зависимости регистрируются при запуске приложения.

## Проверка соответствия

| Что проверяется | Способ |
|---|---|
| Каталог сервисов и порядок | `GET /services`: сравнить полный ответ. |
| Создание, чтение, изменение, удаление, JSON и ошибки | HTTP-тесты с правильными, пустыми и неверными полями; запросы с отсутствующим и неверным `id`. |
| Связь один ко многим и ограничения | Создать две подписки одного сервиса; проверить ошибки при неизвестном `ServiceId`, неположительной сумме и несуществующей дате. |
| Напоминания и сортировка | Создать платежи на `date - 1`, `date`, `date + 3`, `date + 4`; проверить список и порядок. Отдельно проверить переход месяца и года. |
| Сохранение | Создать подписку, перезапустить сервис с той же БД, получить её через API. |
| Типы столбцов, отсутствие строковых полей и внешний ключ | Проверить схему БД: `NextPaymentDate DATE`, остальные столбцы целочисленные, внешний ключ существует. |
| Три слоя и интерфейс репозитория | Проверить зависимости проектов/классов и подменить `ISubscriptionRepository` в модульном тесте бизнес-логики. |

Поведение проверяется тестами, структура — проверкой схемы и кода. В отчёте для каждого пункта фиксируются требование, проверка и вывод «соответствует / не соответствует».
